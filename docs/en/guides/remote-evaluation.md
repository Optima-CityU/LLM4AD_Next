# Remote evaluation gateways

Use a workstation, cluster frontend or laboratory machine to evaluate candidates generated by the web platform. The gateway opens outbound HTTPS connections and receives notifications over Server-Sent Events (SSE); no inbound port is required on that machine. Install Python 3.12+ and the same LLM4AD release as the platform, plus your evaluator's local dependencies.

## Install the SDK and choose how to start

The PyPI distribution is `llm4ad-next`; its CLI is `llm4ad`. Gateway implementation,
optional adapters and deployment files are packaged under `llm4ad/gateway/`.

```bash
pip install -U llm4ad-next
llm4ad evaluator-gateway start --adapter example --server https://YOUR_PLATFORM_HOST --name lab --allow-user YOUR_USER_UUID
llm4ad evaluator-gateway check --adapter example
llm4ad evaluator-gateway source --adapter hgamey
```

### Optional local dashboard

Install the optional NiceGUI 4.0.x dashboard and start the same gateway:

```bash
pip install -U 'llm4ad-next[gateway-ui]'
llm4ad evaluator-gateway start
```

The dashboard opens at `http://127.0.0.1:8768`. Its first page accepts missing
required values, including the gateway name, allowed platform user UUIDs and
evaluator selection, before connecting. The default platform URL is
`https://llm4ad-next.cn`; change it on the page, with `--server`, in the JSON
configuration or through `LLM4AD_SERVER_URL`. Use `--no-open-browser` to serve the
dashboard without opening a browser, or `--no-ui` to run headlessly. Installing
the base package and running existing headless commands requires no UI packages;
NiceGUI, FastAPI and Uvicorn are imported only when the dashboard is enabled.

Configuration priority is explicit CLI flags > explicit `--config` JSON > saved
dashboard settings > environment > defaults. A higher-priority startup value must
be changed at its source. Name, allowed users, concurrency and cleanup policy can
be updated while running. Changes to the server, evaluator or state directory
wait for active jobs, external cleanup/restoration and result/artifact upload
acknowledgements before applying. The page shows pending changes during this wait.

Set `LLM4AD_GATEWAY_UI_PASSWORD` for the independent local dashboard password.
The dashboard requires an independent local password for remote access;
it does not use platform credentials. Keep recovery secrets and raw credentials
out of screenshots and shared configuration. Loopback is the default bind address;
an SSH tunnel can provide remote access while retaining it:

```bash
ssh -L 8768:127.0.0.1:8768 YOUR_GATEWAY_HOST
```

An exported SDK keeps its original four lean dependencies in `requirements.txt`.
For a dashboard, install `requirements-ui.txt`, which includes that file and the
dependencies derived from the package's `gateway-ui` extra. Dashboard sources are
copied into the export without importing UI dependencies during export or core use.

Direct startup requires no generated project or source export. `source` shows the
actual installed `sdk/`, separate `templates/`, and each complete case under
`examples/`, including its own compilation, execution, ADB, backend hooks and deployment
files, without starting a service or probing hardware. A custom evaluator is loaded
with `--evaluator ./evaluator.py:Evaluator` or `package.module:Class`.
An ordinary adapter declares its contract and implements evaluation: compilation,
execution, local datasets and scoring. The SDK owns candidate scheduling, queue and
concurrency limits, transport reconnection, durable reports, local worker recovery,
process-tree cancellation, deadlines, progress and artifacts. Integrations with an
external scheduler or shared device may add resource-specific coordination.

### Optional templates and Docker

Users wanting editable starter files can choose the optional scaffolding path:

```bash
llm4ad evaluator-gateway init ./my-gateway --server https://YOUR_PLATFORM_HOST --name lab --allow-user YOUR_USER_UUID
cd my-gateway
llm4ad evaluator-gateway check --evaluator ./evaluator.py:Evaluator --candidate ./candidate
docker compose up -d --build
```

Templates copy the installed example implementation, protect existing files and
provide editable Docker/Compose settings. Users may extend the example, toolchain
and requirements, or supply their own launcher/container. All paths use the same
SDK. Before this source release is published, a built `llm4ad_next-*.whl` in the
workspace's `wheels/` takes priority over PyPI installation.

Standard `docker compose up -d --build` installs `gateway-ui` and starts the
dashboard in the same gateway container by default. Both PyPI and local-wheel
installation include the extra. Containers use `--no-open-browser`; open
`http://127.0.0.1:8768` yourself.

For basic/custom bridge containers, `LLM4AD_GATEWAY_UI_HOST` and
`LLM4AD_GATEWAY_UI_PORT` select the published host address and port (default
`127.0.0.1:8768`); the container listens on `0.0.0.0:8768`. HGamey retains host
networking for wireless ADB, so the same variables directly select its listener
address and port, without a Compose port mapping. Its internal executor port
8767 remains private. Set `LLM4AD_GATEWAY_UI_PASSWORD` in the runtime `env_file`
for basic/HGamey; custom templates pass it from Compose's environment file or host
environment. This independent local password is required for remote UI access.

Set `LLM4AD_GATEWAY_UI=false` to run headlessly with complete gateway settings.
The UI extra remains installed. Existing commands using
`-f compose.yaml -f compose.ui.yaml` are still supported with the same environment
parameters; the override is no longer needed to enable the dashboard.

Reusable files live in `templates/custom/`. Complete cases live in `examples/`,
with their own source, configuration and `deployment/` together. The basic case
provides a direct SDK Dockerfile, Compose and environment example. Its configuration
requires explicit absolute `LLM4AD_GATEWAY_ENV_FILE` and
`LLM4AD_GATEWAY_DATA_DIR` settings. Pass your environment file with `--env-file`.
`GATEWAY_BASE_IMAGE`, `LLM4AD_PACKAGE` and `PIP_INDEX_URL` are configurable. Users
can instead implement their own container entrypoint and retain the state volume.

### Shared lifecycle and health

Ordinary custom evaluators and HGamey use the same SDK service. Define `contract`
and implement `GatewayEvaluator.evaluate()`; ordinary adapters need no scheduling,
recovery or cancellation implementation. The SDK manages worker execution leases,
replays confirmed-stopped local workers without external saved handles, and handles
local cancellation and timeouts. Optional `before_task()` / `after_task()` hooks
can prepare resources and observe operation outcomes. External work may add
`recover()` / `cancel()` to reconcile its domain-specific state. A persistent local
backend may supply `create_runtime()` hooks for its resources, readiness and
restoration policy; it does not duplicate service, health or cleanup infrastructure.

```bash
llm4ad evaluator-gateway health --state-dir /your/gateway-state
```

Templates and case containers use this common probe. Local/backend readiness and
platform connectivity remain separate, and probing never triggers a new evaluation.
Shared settings are `LLM4AD_GATEWAY_CLEANUP_ENABLED`,
`LLM4AD_GATEWAY_CLEANUP_INTERVAL_SECONDS`, `LLM4AD_GATEWAY_EVIDENCE_KEEP_SECONDS`.
Cleanup waits for upload acknowledgement and optional external-restoration checks.

### Configuration and optional hardware

Supported connection settings are `LLM4AD_SERVER_URL`, `LLM4AD_GATEWAY_NAME`,
comma-separated `LLM4AD_ALLOWED_USER_IDS`, `LLM4AD_GATEWAY_ADAPTER`,
`LLM4AD_EVALUATOR`, `LLM4AD_GATEWAY_STATE_DIR` and `LLM4AD_GATEWAY_CONCURRENCY`.
`--config gateway.json` reads a JSON environment mapping: explicit flags override
config, saved dashboard values, environment and defaults in that order. Custom
environment settings reach adapter processes too.

`--adapter hgamey` selects the packaged Genshin adapter and serialized executor.
The case includes its HGamey Rust/C++/Android source and build scripts. Its
Dockerfile builds phonefarm, Vulkan layer, device runner and refbench APK, and
prepares ADB, NDK and trace tools without a private runtime image. Direct system
startup needs equivalent tools. Phone Root, wireless authorization, official game
installation, test APK installation and real reference frames are covered by the
environment requirements below. Native dependencies remain optional to the generic SDK and are
not downloaded when a gateway receives evaluation work.
HGamey device and game parameters stay in the case's existing environment/JSON
files; its gateway concurrency remains 1 per device. The dashboard configures
common gateway settings and observes the same gateway/executor service.

#### HGamey Genshin environment requirements

The generic gateway runs with Python 3.12+ through Python/CLI or Docker. Its
cross-platform support does not imply portability of this Android hardware case.
The current HGamey recipe targets **Linux amd64**, using Docker Compose host
networking for wireless ADB. This case has not been verified on macOS, Windows or
ARM64 hosts; use a Linux amd64 machine that can reach the phone.

| Layer | Dependencies | Provisioning |
| --- | --- | --- |
| Generic gateway | Python 3.12+, a platform-compatible `llm4ad-next`; optional `gateway-ui` extra for the dashboard | Install directly or through the case's container image |
| Native build | Rust 1.99, OpenJDK 17, host C++, Bash, unzip, file; NDK r27d (27.3.13750724), Android SDK API 35 and build-tools 35.0.0 | The Dockerfile supplies these at build time; prepare equivalent tools for direct execution |
| Local execution | phonefarm, GLSL compiler, SPIR-V validator, ADB 36.0.2, FFmpeg, NumPy, Pillow, Perfetto Python 0.59.1 and official Trace Processor | Included in the image; configure equivalent executable paths for direct execution |
| Phone | Rooted Android 11+ ARM64, Vulkan 1.1 compute with GPU timestamps, accessible Qualcomm KGSL or MediaTek GED frequency controls and readback | Operator-owned device; GPU branding alone does not establish compatibility |
| Evaluation inputs | Authorized Genshin PNG/JPEG references, physical device serial, wireless endpoint, authorized ADB identity and persistent state directories | Operator-provided; not bundled with the SDK |

The image builds the Android ARM64 operator runner, Vulkan layer and refbench APK
from included source; it does not assume the phone already has them installed.
With phonefarm, authorized ADB and build outputs prepared, use
`adb -s YOUR_WIRELESS_ADDRESS shell getprop ro.serialno` to check connectivity and device identity, and install
the test application with `adb -s YOUR_WIRELESS_ADDRESS install -r refbench-mali.apk`.
Install Genshin through its official distribution, finish resource downloads and
sign in yourself. Root access and ADB authorization also require operator setup;
the container does not acquire privileges, accounts or game resources.
GPU dispatch runs on the phone, so the gateway host does not require CUDA. Reference
images must be at least 1920×1080. The current headless quality check center-crops
only the first reference frame; it does not validate multiple scenes or temporal quality.

Game validation additionally needs world entry, successful Vulkan layer loading
and the relevant frame/trace sources. Adjust `game-check.json` resolution, waiting
times and `enter_script` for the device and game's entry screen. Linux containers
need an explicit entry script; the upstream automatic OCR path requires macOS.
Power measurement is disabled by default; unavailable values remain unavailable,
and GPU time is not converted into power.

The first build downloads Rust crates, Android tools, Python packages and Trace
Processor, rather than fetching them when a candidate arrives. Source overrides
are `APT_MIRROR`, `CARGO_REGISTRY_MIRROR`, `ANDROID_REPOSITORY_BASE`,
`PIP_INDEX_URL` and `TRACE_PROCESSOR_URL`; replacement downloads must retain the
required checksums. Wireless ADB does not require a persistent USB connection.
State directories must be writable by container UID 1000. Each phone evaluates
serially with its own lock, identity and state. Keep ADB/signing keys, actual
reference images, `.env` and device configuration local.

This source change has not been released to PyPI. Install the built wheel to use
these entry points before the normal release/version process.

## Start a gateway

Copy **My user ID** from account settings or the task's remote evaluator section. Implement an adapter (see `examples/remote_evaluation/evaluator.py`) and run this command on Linux, macOS or Windows PowerShell:

```bash
llm4ad evaluator-gateway start --server https://llm4ad-next.cn --name lab-workstation --allow-user YOUR_USER_UUID --evaluator ./evaluator.py:Evaluator --state-dir ./.llm4ad-gateway --concurrency 2
```

Repeat `--allow-user` to share with additional users. Registration does not require a platform login token. The CLI generates an independent recovery secret and stores it in `identity.json`; the server keeps its hash. Keep the entire state directory across restarts, and use a different directory per gateway/platform. Only one CLI instance can hold a state directory at a time. Use the dashboard to update sharing or capacity live, or restart headless mode with the same state directory and updated flags.

The gateway runs user code with the permissions of its local account. Use your existing isolated evaluation environment. It does not download platform model credentials or your task's runtime configuration.

## Adapter contract

Subclass `llm4ad.gateway.sdk.GatewayEvaluator`, declare an `EvaluationContract`, and implement `async evaluate(job, reporter) -> EvaluationResult`. The example runs `solution.py:solve(x)` in a real subprocess and returns negative mean squared error as its score. LLM4AD's aggregate score is higher-is-better; declare each individual metric's `minimize`/`maximize` direction accurately.

| Field | Meaning |
| --- | --- |
| `contract.evaluator_id` / `version` | Stable evaluator identity and implementation version |
| `contract.data_version` | Version of the evaluator-local dataset |
| `contract.metrics` | Existing `Metric` definitions, including direction and weight |
| `job.id` / `attempt_id` | Stable job identity and a fenced execution attempt |
| `job.project_root` | Extracted candidate source directory |
| `job.timeout` | Whole-candidate execution budget, in seconds |
| `job.evaluation_profile` | `standard` or `elite`, as requested by the algorithm |
| `job.behavior_storage` | Existing behavior output preference |
| `job.parameters` | Explicit evaluator parameters from task configuration |
| `reporter.progress(message, completed, total)` | Observed progress; counts are optional |
| `reporter.message(text, level="info", data={})` | Durable diagnostic message without changing progress or deadlines |
| `reporter.metadata(dict)` | Merge JSON-compatible context before a result exists |
| `reporter.artifact(name, path, media_type, description="...")` | Snapshot a declared file and retain its explanation |
| `reporter.save_state(dict)` | Durable external scheduler handle for recovery |
| `reporter.saved_state` | Last saved external execution information |

Each job represents **one entire candidate**, including all instances/seeds you choose to run. Your `evaluate()` implementation chooses the local data and measurements and aggregates their scores. The SDK queues and schedules candidates within the configured gateway concurrency limit. Only integrations with external execution systems need their own scheduler submission or resource-specific coordination; an ordinary evaluator does not implement the gateway's scheduling or recovery state machine.

The execution layer uses bounded, isolated per-job processes rather than a reusable `joblib.Parallel` pool. This keeps forced cancellation scoped to one evaluation and its child processes. Joblib's running futures do not support individual cancellation; its backend's abort operation stops the executor's tasks as a group ([official backend documentation](https://joblib.readthedocs.io/en/stable/user_guide/custom_parallel_backend.html)). An evaluator may optionally use joblib internally for independent data instances, but it does not replace the SDK's durable queue or recovery state. The lightweight gateway does not require joblib; an adapter using it declares that dependency in its own environment.

Optional operation hooks are `before_task(job, reporter, operation)` and
`after_task(job, reporter, operation, *, result=None, error=None)`, where
`operation` is `"evaluate"`, `"recover"` or `"cancel"`. Use them for preparation,
diagnostics and cleanup around an operation. The after hook receives its result or
error, including an error raised by the before hook. A hook failure does not replace
an existing domain error. For `"cancel"`, the before hook precedes the SDK's durable
stop request, local process-tree termination and external cancellation confirmation.
The after hook receives the boolean confirmation result, which can be `False` while
cancellation is pending, or an error. These hooks supplement the evaluation logic;
execution ownership, replay, cancellation confirmation, deadlines and durable
reporting remain authoritative SDK responsibilities. Ordinary adapters need no hooks.

Messages and progress events are ordered and saved per execution attempt in the local journal. Live reports carry the latest text; full history is retained in `metadata.evaluation_messages`, including timestamps, levels and structured `data`. Metadata and messages survive gateway restarts and are merged into the final result. They do not replace `save_state`, which is reserved for external execution handles. Old attempts cannot modify the current attempt's observations.

### Events, local output and lifecycle timing

The dashboard's event view reads `reporter.message()` and `reporter.progress()`
records. It initially shows the latest 100 matching events, with level/text filters,
older history and incremental updates using exclusive sequence cursors. All reads
are fenced to the selected binding, job and attempt. Existing page-based message
APIs remain available.

Local execution logs are a separate view of actual worker/child-process stdout
and stderr. They are not event messages and are never automatically uploaded as
platform artifacts. An evaluator can create another explicitly named source:

```python
log_path = reporter.local_log("solver.stdout", description="Solver process stdout")
with log_path.open("ab") as output:
    subprocess.run(command, stdout=output, stderr=subprocess.STDOUT, check=True)
```

A backend may implement `runtime.local_logs(job, saved_state)` to return a mapping
of readable source names to owned local files. Discovery uses accepted local
receipts; it must not start an evaluation, readiness check or external process.
The dashboard lists only registered sources, supports bounded byte reads and
downloads a temporary snapshot. Paths and saved recovery state are not exposed
in source metadata. Explicit `EvaluationArtifact` declarations retain their normal
platform upload behavior.

Local log copies have independent seven-day retention, configured by
`LLM4AD_GATEWAY_LOG_KEEP_SECONDS` (`local_log_keep_seconds`, default `604800`).
The shared collector expires completed, inactive local copies only after any
backend ownership/restoration guard confirms cleanup is safe. Unconfirmed external
work keeps its logs. This separate policy does not change report/artifact
acknowledgements or evidence retention. Active execution logs are kept;
expired sources remain recognizable as unavailable. Local log retention can be
updated without restarting the gateway.

Task details show actual `started_at`, `finished_at` and wall-clock `elapsed_ms`,
including preparation and finalization hooks. The evaluator's `duration_ms` stays
unchanged and may measure only its own evaluation. Missing legacy dates remain
`null`; an update timestamp is not treated as a completion timestamp. Current
`metadata.lifecycle` and `lifecycle_stages` record preparing/evaluating/finalizing
and running/completed/failed observations. Private local lifecycle observations
also preserve finalization that occurs after a terminal report is fenced.
Individual cases provide their own hook behavior and additional source labels.

Startup readiness records use a separate local journal. The dashboard can inspect
the latest startup summary, events and local logs with `purpose="startup"` without
starting a new check. These records are not platform evaluation jobs or results.

Return `EvaluationResult` for measured outcomes, including `success=False` for a measured failure. It supports `metrics`, auxiliary `monitor_metrics`, `metadata`, `evolution_feedback`, `duration_ms`, behavior output and explicit `artifacts`. The SDK supplies elapsed worker time when duration is omitted. Both successful and failed final results retain extra data and attachments through the platform's existing evaluation-detail storage. Attachments are uploaded before the final result is acknowledged; this does not provide live file preview during execution.

For a known failure, raise `EvaluationError(message, metadata=..., evolution_feedback=..., artifacts=...)` from `llm4ad.gateway.sdk`. Unexpected worker exceptions use the same reporting path, retaining their type, message and a traceback attachment; `subprocess.CalledProcessError` also retains stdout, stderr and return code when available. Optional file capture errors are recorded in `metadata.artifact_errors` without changing a measured score. Raise `EvaluationUnavailableError` when a resource or execution outcome is unavailable: the job waits in `recovery_required`, rather than scoring the candidate or automatically repeating external work. External integrations can retain handles with `save_state` and implement optional `recover`/`cancel` overrides to interpret them; ordinary local evaluation uses the SDK defaults.

By default only recognized source files and build manifests are transferred. `config.yaml`, `.env*`, runtime state and `data/`/`datasets/` are excluded. Use `candidate_paths` (relative glob patterns such as `['src/**/*.py', 'assets/*.txt']`) for additional candidate resources. Your adapter should locate its own evaluator/data files relative to `__file__` or a local absolute path: its working directory is the candidate, not the adapter directory.

## Configure a web task

In the existing task configuration steps, choose **Remote evaluator**, then select one or more gateways shared with your user ID. A pool must declare the same evaluation contract. Every candidate goes to one selected gateway; multiple gateways share queued candidates rather than evaluate the same candidate repeatedly. Offline gateways remain selectable, and tasks can wait for them to reconnect.

An equivalent evaluator section is:

```yaml
evaluator:
  type: remote
  gateway_ids:
    - YOUR_GATEWAY_UUID
  timeout: 300
  parallel: true
  batch_size: 4
  candidate_paths: ["solution.py"]
  parameters: {}
```

The platform resolves and validates the contract before starting. Remote submission requires the platform task runtime; standalone `llm4ad run` does not create a remote platform task. Candidate sources and EVOLVE blocks are still required on the platform, while evaluator code, datasets and their dependencies stay on the gateway. The workbench's **Remote evaluation** tab shows the latest 100 jobs, gateway connectivity, real progress and scores.

## Disconnect, recover and cancel

- The SDK retains accepted work, progress and results in SQLite. Network loss does not stop local evaluation or turn a queued candidate into a failed one. HTTP reports carry monotonic sequences; duplicate results count once.
- Accepted work stays assigned to its original gateway. A stale heartbeat never transfers it to another gateway. Waiting for a gateway or capacity does not consume the execution timeout.
- The SDK manages an execution lease for each local worker, including a worker that survives its gateway process. It waits for that worker to stop before replay. After a gateway restart, unfinished local work without external saved handles can be replayed once the SDK confirms the previous worker has stopped. Default replay clears unfinished SDK output files that have not been uploaded and resets execution timing, while preserving message history. It calls `evaluate()` again from the beginning; it does not restore an arbitrary Python stack checkpoint. An adapter needs no `recover()` override for this local replay.
- A separate process-tree guardian retains ownership while descendants are being terminated, including children that ignore graceful termination. Unconfirmed process-tree termination remains uncertain rather than becoming permission to replay. Hook instances are process-local; use the journal/recovery handle for context that must survive termination. A forced kill cannot execute worker-local Python finalizers, while cancellation hooks run in the gateway around its stop/confirmation operation.
- Actual execution is timed locally, even when the platform cannot be reached. Local process trees are stopped at the deadline. If an external scheduler handle exists, a timeout/crash preserves an uncertain state so that external work can be reconciled.
- Platform stop cancels queued jobs and requests cancellation of accepted work. The SDK durably records received cancellation requests, stops the local process tree and uses its default cancellation behavior for ordinary evaluators. A recorded cancellation remains in force across restarts and prevents local replay of that job.
- External saved handles require domain-specific reconciliation: optional `recover(job, reporter)` reconnects using `reporter.saved_state` and returns the existing result, or `None` if it cannot be determined. Optional `cancel(job, saved_state) -> bool` returns `True` only after external cancellation is confirmed. These overrides remain supported for integrations such as HGamey; the SDK still orchestrates the lifecycle. An unresolved external cancellation retains its gateway slot. Do not blindly repeat external experiments; use `job.id`/`attempt_id` as scheduler idempotency keys and persist submission intent/handles before waiting.
- If uncertain work still needs manual resolution, first check that old execution has stopped, then use the commands below. `retry` creates a new fenced server attempt, which can be claimed by a compatible selected gateway. An old attempt's result is rejected.

```bash
llm4ad evaluator-gateway status --state-dir ./.llm4ad-gateway
llm4ad evaluator-gateway resolve JOB_UUID --action retry --state-dir ./.llm4ad-gateway
llm4ad evaluator-gateway resolve JOB_UUID --action cancelled --state-dir ./.llm4ad-gateway
```

Restart the gateway with the same command/state directory after a crash. Accepted jobs recorded as never started resume automatically. A legacy journal entry already marked running but lacking SDK execution-control records remains uncertain and needs reconciliation; the SDK cannot confirm that old execution stopped. A missing journal also preserves uncertainty. Exactly-once execution inside an external scheduler depends on your adapter's recovery/idempotency support. The platform cannot forcibly kill processes on an offline machine; cancellation is reconciled on reconnection.

## Platform deployment

The [Genshin Shader gateway source](../../../src/llm4ad/gateway/examples/hgamey/)
provides an SDK-loadable adapter, fixed baseline, real compilation, private local
reference frames, recovery and an extracted-executor compatibility patch. Select
the `hgamey_shader` example in the task wizard, then bind a model and an authorized
gateway. It measures isolated operator performance; in-game FPS gains require
separate device evidence.

Apply the included Alembic migration and rebuild backend, workers, task-runner and frontend. Standard `docker/compose.yml` includes a dedicated `remote-evaluation-worker` consuming `remote_evaluation`. `REMOTE_EVALUATION_CONCURRENCY` defaults to 10. Remote tasks renew their execution lease and model proxy credentials while waiting; existing local tasks retain their normal timeouts.

For a production checkout using `compose-cloud.yml`, enable the portable override (keep your other production overrides):

For model credentials to remain usable after a long offline wait, enable `LLM_PROXY_ENABLE=True` and configure `LLM_PROXY_BASE_URL` for task containers. This also refreshes builtin-provider access tokens on demand; direct provider URLs retain their original token expiry.

```bash
cd docker
LLM4AD_COMPOSE_BASE=compose-cloud.yml docker compose -f compose-cloud.yml -f compose.remote-evaluation.yml up -d --build
```

Set `LLM4AD_COMPOSE_BASE` in `.env` when using PowerShell. SSE notifications use an authenticated HTTP GET with a keepalive event every 10 seconds. The stream reconnects after disconnection, read timeout or a proxy error, with a two-second retry delay. Its lifetime is independent of ordinary HTTP request timeouts. HTTP heartbeats continue to reconcile jobs when SSE is unavailable; durable claim/report/status operations and accepted-job ownership do not depend on receiving every notification. No new public gateway listener or Docker socket exposure is required on the user's evaluator machine. Update both the platform backend and the gateway SDK (or its exported container runtime) for the SSE transport.

## Returning evaluation evidence

Before returning a result, a custom evaluator can call
`reporter.artifact("trace.pftrace", local_path, "application/octet-stream")`.
The SDK spools an immutable copy with its SHA-256 and durable upload receipt,
uploads evidence before the final result, and retries transfers without repeating
evaluation. Files are stored separately in RustFS/S3. `metadata.artifacts`
contains a manifest and task-owner authenticated download paths; binary data is
not stored in SQL result rows or base64 JSON. Update both backend and gateway SDK.

## Evaluation details and retained files

The task workbench's **Evaluation details** tab is shared by local and remote evaluators. Select a candidate and evaluation stage to inspect metrics, per-instance metadata and retained files. JSON, text, Markdown and supported images can be previewed; traces and other formats can be downloaded. Historical `reporter.artifact()` results remain readable.

For a local evaluator, write outputs inside `cfg.artifact_dir` and return explicit declarations:

```python
from pathlib import Path
from llm4ad.evaluator import EvaluationArtifact, EvaluationResult

report = Path(cfg.artifact_dir) / "report.json"
report.write_text('{"measured": true}', encoding="utf-8")
return EvaluationResult(
    score=score,
    metrics=metrics,
    artifacts=[EvaluationArtifact(
        name="reports/report.json", path="report.json", media_type="application/json"
    )],
)
```

Remote adapters may continue calling `reporter.artifact()`, or write inside `job.artifact_dir` and return the same declarations. Files and full JSON records live in RustFS, scoped to the exact task version, candidate, source fingerprint, stage and instance. Only explicitly declared files and returned behavior visualizations are retained; temporary directories, screenshots and videos are not automatically collected.

Uploads retry independently of evaluation. Local snapshots are removed only after durable file/manifest acknowledgement; custom adapter retention continues to own external evidence. Platform files remain until task deletion. The preview limit is configured by `EVALUATION_PREVIEW_MAX_BYTES` (default 2 MiB); this affects preview only, not original-file downloads. The lightweight `examples/evaluation_artifacts` example runs without an LLM or device.
